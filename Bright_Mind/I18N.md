# Internationalization

Internationalization is mandatory for every new Bright Mind feature that exposes user-facing content.

## Initial locale scope

The platform must be able to support at least the relevant languages for Poland, Spain, Bulgaria, Greece, Ireland, and Italy. Exact locale codes, source-language policy, and launch-language matrix will be confirmed during planning.

The initial application locale set is English (`en`), Polish (`pl`), Spanish (`es`), Bulgarian (`bg`), Greek (`el`), and Italian (`it`). Keep this canonical list in `config/locales.php`; frontend locale presentation is defined once in `resources/js/i18n/locales.ts`.

The selected UI locale is applied by `SetLocale`. Authenticated users persist it in `users.preferred_locale`; guests use the `bm_locale` cookie and session, with local storage providing client-side continuity. Inertia shares the active locale as the `locale` prop.

## Two translation domains

Keep these concepts separate:

1. **Application UI copy** — navigation, buttons, forms, validation, system notifications, emails, generic labels.
2. **Managed educational/content copy** — courses, blocks, activities, pathways, badges, assessment content, resources, admin-managed messages.

They may use different storage/workflow mechanisms while sharing locale/fallback conventions.

## Required content workflow capabilities

The planned content system must support:

- source-language content
- per-locale translations
- machine translation through DeepL where appropriate
- manual editing of machine output
- translation status
- reviewer/approval metadata
- stale/outdated detection when source content changes
- per-language preview
- fallback behavior
- translatable activity fields
- alternate media/video versions per locale where required

Candidate translation states:

`missing -> machine_translated -> needs_review -> reviewed -> approved`

A previously translated record may also become `outdated` after its source changes. Exact workflow remains an open design decision.

## Engineering rules

- Do not scatter new hard-coded user-facing strings throughout Bright Mind features.
- Do not store translatable activity/course content in opaque structures that make per-field translation impossible to manage.
- Translation metadata must remain queryable for admin dashboards and completion checks.
- Every reusable activity type must declare which properties are translatable.
- User-generated/partner-generated content must be designed for translation from its first schema version.
- Validation/system messages should participate in the application locale system.
- Accessibility text such as alternative text, captions, and transcripts is translatable content where relevant.

## DeepL

DeepL is planned, not implemented. The final design should support queued translation requests, retries, usage/error handling, source/target locale mapping, editable results, and provenance metadata. Do not couple core content storage directly to DeepL-specific response formats.

## Search

Search requirements must account for locale. Avoid selecting a search engine until content scale, filtering, stemming, typo tolerance, and cross-language requirements are defined.
